# Authlode SSO 用户管理平台 - 总体技术方案 v4.0

> 定位与功能/实现总纲见 [SSO平台功能目标与实现方案.md](SSO平台功能目标与实现方案.md)（当前权威）；本文提供架构细节。

## 📋 项目概述

### 项目名称
**Authlode** (SSO 用户管理平台 / SSO User Management Platform)

### 项目定位

这是一个 **SSO 用户管理平台**: 以 IAM 为身份底座 (Logto 为第一实现平台),面向多租户提供用户全生命周期管理与 SSO 应用接入管理。租户管理员在本平台自助完成租户内的全部管理工作,无需平台运营方介入;用户一次登录,通行租户内所有已接入应用与平台本身。

- **平台无关**: 通过 IAM Provider 抽象层对接底层身份平台,系统本身不绑定特定 IAM
- **Logto 为第一实现平台**: 首个 Adapter 基于 Logto Management API 实现,后续可扩展 Keycloak、Authentik 等其他 IAM
- **租户自管理**: 租户管理员管理本租户的用户、组织、权限、应用接入配置,数据按租户隔离
- **邀请注册**: 租户可自行邀请用户注册 (邀请链接 → 自助注册 → 自动入组授权)
- **数据分层**: 身份数据 (用户/角色/权限) 存储于 IAM 平台;**租户是平台自有概念** — 租户、租户内组织、应用接入、邀请等存储于扩展数据库,按租户隔离

### 多租户模型 (2026-09-18 确认)

| 决策点 | 结论 |
|--------|------|
| 隔离模型 | **软隔离** — 单 Logto 实例,**Logto Organization 映射为租户**;同一 email 跨租户为同一账号 (视为 SSO 特性),租户间数据靠查询隔离 (所有查询强制 tenantId 过滤)。**术语约定**: 租户 = **接入的系统**(业务系统/应用) — 多租户即多系统: 账号体系统一、系统间隔离、一个用户可用多个系统 |
| 租户开通 | **运营方预置,全程在 IAM 自带管理后台完成** — 运营方在 Logto Admin Console 创建 Organization (= 租户) 并任命首个租户管理员 (授予 org role);Authlode 侧 Tenant 记录在首次登录时 **JIT 自动创建**;系统不含自助创建租户流程,无平台端 |
| 管理界面分工 | **系统级管理 = IAM 自带后台 (Logto Admin Console),Authlode 只做租户后台** — Authlode 不重复建设 IAM 实例管理功能;此原则平台无关 (Keycloak/Authentik 等亦各自带管理后台) |
| 租户管理员识别 | 映射为 **Logto Organization 角色** (如 `tenant-admin`),运营方可直接在 Logto 后台任命;TenantContext 中间件经 Provider 查询 org role 判定 |
| 租户内组织 | Logto Organizations 为扁平结构且已被用作租户,**租户内的组织/部门树存储于扩展数据库** (平台自有数据) |
| 邀请注册语义 | 双语义: 新 email = 注册新账号 + 入租户;已有 email = 邀请加入租户 (复用既有账号) |
| 认证与授权分工 | 认证 (authentication) 由 IAM 的 OIDC 完成,token 只证明身份;**租户上下文与租户内授权 (authorization) 由平台解析** (TenantContext 中间件 + 扩展库租户成员关系);预留 break-glass 本地管理员应对 IAM 故障 |
| 应用接入拆分 | IAM 应用注册表 (A 类,经 Provider 读写) 与**租户应用接入配置** (B 类,扩展库) 是两个概念 |

**租户开通流程** (运营方全程在 Logto Admin Console 操作,Authlode 侧零配置):

1. 运营方在 Logto Admin Console 创建 Organization (= 租户)
2. 运营方将首个租户管理员加入 Organization,授予 `tenant-admin` org role
3. 该管理员首次登录 Authlode: OIDC 认证 → TenantContext 发现无 Tenant 记录 → **JIT 自动创建** (tenantId = Organization ID) → 租户自管理开始

> 注 1: 用户属于多个租户时 (软隔离的 SSO 特性),租户后台提供租户切换器。
> 注 2: 跨租户的运营数据 (如全平台审计汇总) Logto 后台无法覆盖 — v1 不做,属部署工具/数据库层面。

**机制示例** (两个租户 Acme/Beta,**同一个** Logto 实例):

```
1. 运营方 (一次性, 在 Logto 后台):
   建 Organization "Acme" → 建 alice@acme.com → 加入 Acme → 授 tenant-admin

2. Alice 登录 Authlode:
   OIDC 认证 → 查到她属 Acme 且是管理员 → 进入 Acme 管理界面

3. Alice 邀请 bob@acme.com:
   ├─ Bob 没注册过 → 邀请链接 → 注册页设密码 → 建号 → 自动入 Acme + 角色
   └─ Bob 注册过 (曾在 Beta) → 邀请链接 → 登录 → 直接入 Acme
        → 同一账号、两个租户、各自独立角色 (Acme 成员 / Beta 管理员)

4. 隔离:
   Beta 的管理员看不到 Bob 在 Acme 的任何数据
   (扩展库查询强制 tenantId 过滤; Logto 侧按组织查询)
```

**多租户机制归纳为三件事**: ① 分组 (Organization,Logto 原生) ② 角色 (用户×组织各自独立,Logto 原生) ③ 过滤 (自有数据带 tenantId 强制隔离,平台实现)。账号池全局共享 (同 email 同账号) 是 SSO 特性而非隔离漏洞。

**对现有模块的影响**:
- `organizations` 模块 (操作 Logto Organizations) 语义变为**租户** — 属运营方关注点 (在 Logto Admin Console 管理);租户端界面的"组织管理"改为管理扩展库中的租户内组织树
- `applications` 模块需拆分: IAM 应用注册 (Provider) vs 租户应用接入配置 (扩展库)
- `invitations` 模块需支持双语义 (新账号注册 / 既有用户加入租户)

### 模块一: 用户管理 (Logto 数据)

#### 功能清单
1. **用户列表查询**
   - 分页查询 (调用 Logto API)
   - 多条件搜索
   - 状态筛选

2. **用户详情查看**
   - 基本信息来自 Logto
   - 扩展信息来自数据库
   - 合并展示

3. **用户信息编辑**
   - 更新 Logto 用户信息
   - 更新扩展数据库信息

4. **用户组织关系**
   - 调用 Logto API 管理关系
   - 查看用户所属组织

5. **用户角色分配**
   - 调用 Logto API 分配角色
   - 查看用户权限

6. **用户状态管理**
   - 启用/禁用 (Logto API)
   - 锁定/解锁

#### 技术实现
```typescript
// 用户服务示例
@Injectable()
export class UsersService {
  constructor(
    private readonly logtoApiService: LogtoApiService,
    private readonly userExtendRepository: UserExtendRepository,
  ) {}

  async findAll(query: UserQueryDto) {
    // 1. 从 Logto API 获取用户列表
    const logtoUsers = await this.logtoApiService.getUsers(query);

    // 2. 获取扩展信息
    const userIds = logtoUsers.data.map(u => u.id);
    const extends = await this.userExtendRepository.findByIds(userIds);

    // 3. 合并数据
    return logtoUsers.data.map(user => ({
      ...user,
      extend: extends.find(e => e.userId === user.id),
    }));
  }

  async update(userId: string, data: UpdateUserDto) {
    // 1. 更新 Logto 用户信息
    if (data.name || data.email) {
      await this.logtoApiService.updateUser(userId, {
        name: data.name,
        email: data.email,
      });
    }

    // 2. 更新扩展信息
    if (data.department || data.position) {
      await this.userExtendRepository.upsert(userId, {
        userId,
        department: data.department,
        position: data.position,
      });
    }
  }
}
```

## 🌐 IAM Provider 抽象层与 Logto Adapter

### 设计原则

系统定义统一的 **`IamProviderInterface`** — 覆盖用户、组织、角色、权限、应用、邀请、认证等身份操作的平台无关契约,由各 IAM 平台的 Adapter 实现:

```typescript
// src/iam/interfaces/iam-provider.interface.ts (规划)
export interface IamProviderInterface {
  // 用户
  getUsers(query): Promise<PagedResult<IamUser>>;
  createUser(data): Promise<IamUser>;
  updateUser(userId, data): Promise<IamUser>;
  deleteUser(userId): Promise<void>;
  // 组织 / 角色 / 权限 / 应用 / 邀请 / OIDC 认证 ...
}
```

- **Logto Adapter 是第一个实现** — 以下代码即 Logto Adapter 的实现参考
- 业务模块 (users/organizations/roles/applications) 只依赖 Provider 接口,不感知具体平台
- 通过配置选择平台: `IAM_PROVIDER=logto` (后续: `keycloak` / `authentik` / ...)
- 新增 IAM 平台 = 新增一个 Adapter 实现,业务代码零改动

### Logto Adapter 封装服务

```typescript
// src/modules/logto/logto-api.service.ts
@Injectable()
export class LogtoApiService {
  private readonly apiEndpoint: string;
  private readonly apiKey: string;

  constructor(private readonly httpService: HttpService) {
    this.apiEndpoint = process.env.LOGTO_MANAGEMENT_API_ENDPOINT;
    this.apiKey = process.env.LOGTO_MANAGEMENT_API_KEY;
  }

  private get headers() {
    return {
      'Authorization': `Bearer ${this.apiKey}`,
      'Content-Type': 'application/json',
    };
  }

  // ============================================
  // 用户 API
  // ============================================

  async getUsers(params: {
    page?: number;
    pageSize?: number;
    search?: string;
  }) {
    const response = await this.httpService.axiosRef.get(
      `${this.apiEndpoint}/users`,
      { params, headers: this.headers }
    );
    return response.data;
  }

  async getUserById(userId: string) {
    const response = await this.httpService.axiosRef.get(
      `${this.apiEndpoint}/users/${userId}`,
      { headers: this.headers }
    );
    return response.data;
  }

  async createUser(data: CreateUserDto) {
    const response = await this.httpService.axiosRef.post(
      `${this.apiEndpoint}/users`,
      data,
      { headers: this.headers }
    );
    return response.data;
  }

  async updateUser(userId: string, data: UpdateUserDto) {
    const response = await this.httpService.axiosRef.patch(
      `${this.apiEndpoint}/users/${userId}`,
      data,
      { headers: this.headers }
    );
    return response.data;
  }

  async deleteUser(userId: string) {
    await this.httpService.axiosRef.delete(
      `${this.apiEndpoint}/users/${userId}`,
      { headers: this.headers }
    );
  }

  // ============================================
  // 组织 API
  // ============================================

  async getOrganizations() {
    const response = await this.httpService.axiosRef.get(
      `${this.apiEndpoint}/organizations`,
      { headers: this.headers }
    );
    return response.data;
  }

  async getOrganizationTree() {
    const orgs = await this.getOrganizations();
    return this.buildTree(orgs);
  }

  async createOrganization(data: CreateOrganizationDto) {
    const response = await this.httpService.axiosRef.post(
      `${this.apiEndpoint}/organizations`,
      data,
      { headers: this.headers }
    );
    return response.data;
  }

  async addOrganizationUser(organizationId: string, userId: string) {
    await this.httpService.axiosRef.post(
      `${this.apiEndpoint}/organizations/${organizationId}/users/${userId}`,
      {},
      { headers: this.headers }
    );
  }

  // ============================================
  // 角色 API
  // ============================================

  async getRoles() {
    const response = await this.httpService.axiosRef.get(
      `${this.apiEndpoint}/roles`,
      { headers: this.headers }
    );
    return response.data;
  }

  async assignRoleToUser(userId: string, roleId: string) {
    await this.httpService.axiosRef.post(
      `${this.apiEndpoint}/users/${userId}/roles`,
      { roleIds: [roleId] },
      { headers: this.headers }
    );
  }

  // ============================================
  // 应用 API
  // ============================================

  async getApplications() {
    const response = await this.httpService.axiosRef.get(
      `${this.apiEndpoint}/applications`,
      { headers: this.headers }
    );
    return response.data;
  }

  // ... 其他 API 方法
}
```

## 🔒 安全设计

### 认证与授权

1. **身份认证**
   - 通过 IAM Provider 进行 OIDC 登录 (Logto 为第一平台)
   - 租户上下文 (Tenant Context) 贯穿认证与授权流程
   - JWT Token 验证
   - Token 刷新机制
   - 预留 break-glass 本地管理员 (IAM 平台故障时的应急入口)

2. **权限控制**
   - 租户管理员角色与租户级权限
   - 基于 IAM 平台的角色权限
   - API 级别权限检查
   - 数据权限过滤 (租户隔离,防越权)

3. **审计追踪**
   - 记录所有管理操作
   - 敏感操作详细记录
   - 异常行为告警

4. **接口边界**
   - 前端**永不直连** IAM Management API (API 密钥仅存于后端)
   - 后端为所有管理操作的必经之路: 前端 → 后端 (token 验证 + TenantContext + tenantId 过滤) → Provider → IAM
   - 认证流程例外: 浏览器与 IAM 的 OIDC 端点直接交互 (授权码流程),后端仅验证 token、不签发

### v4.0 (2026-09-19) — 重新定位为 SSO 用户管理平台

**变更内容**:
- 产品定位从"多租户 IAM 用户管理系统"调整为更通用的 **"SSO 用户管理平台"**

- 新增关键设计点: 访问控制执行点 (Logto 不按组织限制应用登录,需在组织 Token/应用自查/平台鉴权 API 中决策)
- 多租户架构/租户自管理/Provider 抽象等全部既有决策**不变**

**权威文档**: 功能目标与实现方案以 [SSO平台功能目标与实现方案.md](SSO平台功能目标与实现方案.md) (v4.0 研判) 为准;本文架构细节仍有效。

### v3.0 (2026-09-18) — 从 Logto 专用到通用多租户 IAM

**变更内容**:
- 系统从 "Logto 用户中心管理系统" 重新定位为 **"Authlode 多租户 IAM 用户管理系统"**
- 从 Logto 专用管理台 → **平台无关的 IAM 用户管理系统**,Logto 降级为第一个 Provider Adapter
- 新增**多租户**要求: 系统为租户端控制台 (含租户管理员),数据按租户隔离
- 邀请系统升级为**租户自行邀请用户注册**的自助流程 (邀请链接 → 注册 → 入组授权)
- 应用管理升级为**租户级应用接入配置**

**架构影响**:
1. 新增 `IamProviderInterface` 抽象层,现有 `LogtoService` 重构为 Logto Adapter
2. 扩展数据库新增 Tenant 模型,所有扩展表增加 tenantId 隔离字段
3. 邀请流程增加公开注册页面 (邀请 Token 验证,无需登录)
4. 认证授权流程需携带租户上下文 (Tenant Context)

**已决设计决策** (2026-09-18 确认,详见 "项目定位 > 多租户模型"):
- 租户 ↔ Logto 映射: **软隔离** — 单实例,Logto Organization = 租户
- 平台端: **不做** — 租户由运营方预置,系统不含自助开通租户流程
- 层级关系: 租户 (Logto Organization) > 租户内组织/部门 (扩展库) > 用户 (IAM)
