## 一、IAM 集成层

### 1.1 IAM Provider 抽象层 【实现·新建】 P0

**做什么**: 定义 `IamProviderInterface` — 平台无关的身份操作契约，业务模块只依赖此接口。

**接口域**（按总体技术方案 v3.0）:
- 用户: 列表(分页/搜索)/详情/创建/更新/删除/验证密码
- 租户(组织): CRUD/成员增删查/**org 角色**
- 角色/权限: CRUD/分配
- 应用: 注册表 CRUD
- 认证: OIDC 端点/Token 校验
- 能力探测: `getCapabilities()`（不同 IAM 支持度不同，如 per-org SSO）

**现状**: ❌ 完全不存在。现有 `LogtoService` 被业务模块直接注入耦合。

### 1.2 Logto Adapter 【重构】 P0

**做什么**: 将现有 `LogtoService`（`backend/src/logto/logto.service.ts`，743 行）改造为 Adapter 实现。

**已封装（可直接迁移）**:

| 域 | 方法 | 备注 |
|---|---|---|
| 用户 | getUsers / getUserById / createUser / updateUser / deleteUser / verifyUserPassword / sendUserEmailVerification | 分页+搜索+筛选齐全 |
| 组织 | getOrganizations / getOrganizationById / createOrganization / updateOrganization / deleteOrganization | CRUD 齐 |
| 组织成员 | getOrganizationUsers / addOrganizationUser / removeOrganizationUser | **addOrganizationUser 已支持 organizationRoleIds** |
| 角色 | getRoles / getRoleById / createRole / updateRole / deleteRole / assignRoleToUser / removeRoleFromUser | 实例级角色 |
| 应用 | getApplications / getApplicationById / createApplication / updateApplication / deleteApplication | 实例级 |

**缺口（需新增封装）** — Logto 调研已确认全部可行 ✅:
- 查询"用户属于哪些组织": `GET /api/users/{userId}/organizations`（返回组织列表 + 该用户在各组织的 org 角色）— 多租户归属的数据源
- Organization 角色操作: `POST/GET /api/organization-roles`（角色 CRUD）、`POST /api/organizations/{id}/users/{userId}/roles`（按组织分配/查询）— 租户管理员判定的数据源。**注**: org 角色为模板级定义（全实例共享同一套角色集），差异化靠"用户×组织"分配而非按组织自定义角色
- Logto 原生组织邀请 API 存在: `POST /api/organization-invitations`（创建/邮件/状态更新/一次性 Token 全套）— **决策维持**: 邀请记录留自建扩展库（保证 IAM 无关性），Provider 将邀请作为可选能力暴露（能力探测）
- OIDC 认证端点对接（授权码流程/token 交换/JWKS 校验）— 标准 OIDC，待实现
- 创建用户时设置初始密码: `POST /api/users` 支持 `password` 字段（另有 `passwordDigest` 哈希导入）。**注意**: 建用户+入组+授权需 3 次独立调用，**无原子性** — 邀请接受流程需幂等设计（先查后建、失败重试不重复建号）

## 四、核心业务模块

### 4.1 用户管理（租户化） 【混合】 P1

- **集成**: 用户 CRUD/搜索/分页经 Provider（LogtoService 已有，controller 已真调用）
- **实现**: 查询加租户过滤（改为按 org 成员查询而非全实例查询）；用户详情合并 UserExtend（Repository 已有）
- **现状**: ⚠️ `users.controller.ts`（112 行）真实调用；前端 `users.vue` 内联 mock 数组

### 4.2 租户内组织树 【实现】 P1 — 语义改造

- **做什么**: 租户端"组织管理"= 租户内组织/部门树（父子层级），存扩展库
- **现状**: `organizations.controller.ts`（97 行）操作的是 Logto Organizations — 按新定位其语义是"租户"（运营方在 Logto 后台管理），**此模块需整体改造**：新模型（TenantOrganization: tenantId/parentId/name/...）+ 新 Repository
- **注意**: 这是现有代码里语义偏移最大的模块

### 4.3 角色权限 【混合】 P1

- **集成**: 实例级角色 CRUD 已有；**org 角色**（租户内角色）调研确认原生支持（`/api/organization-roles` 模板级定义 + 按用户×组织分配），需新增封装
- **实现**: 角色管理界面按租户上下文过滤（org roles vs 实例级角色的展示策略）；注意 org 角色为模板级（全实例共享角色集），租户差异化靠分配
- **现状**: ⚠️ `roles.controller.ts`（102 行）真实调用，仅实例级

### 4.4 应用接入 【混合】 P1 — 拆分两概念

| 概念 | 类型 | 内容 | 现状 |
|---|---|---|---|
| IAM 应用注册表 | 集成 | Logto Application CRUD（已有） | ⚠️ `applications.controller.ts`（87 行）真实调用 |
| 租户应用接入配置 | 实现 | 新模型（tenantId + 应用关联 + 接入策略）：租户接入/停用应用、租户级访问策略 | ❌ 无 |

> ✅ 调研已确认: 交互式 OIDC 应用为**实例级全局**，不能按组织隔离/分配（仅 M2M 应用可关联组织并授予 org 角色）。租户应用接入配置**必须**由扩展库承载 — 拆分方案成立。租户级 API 授权可另用 Logto 组织 Token / 组织级 API 资源能力（后续可选增强）。
>
> **访问控制已决 (2026-09-19)**: 系统接入默认采用**组织 Token 强制约定** — 非系统成员无法从 IAM 获得该系统令牌（"没资格用不了"由 IAM 执行，接入系统零检查代码）；细粒度资格由 org roles + 扩展库策略承载。见总纲 3.3.2。

### 4.5 邀请注册（双语义）+ 邮件 【混合】 P2 — 当前空壳

- **流程**: 租户管理员创建邀请（email+角色+组织）→ 邮件发送 → **公开注册页**（Token 验证，无需登录）→ 双语义处理（新 email = 经 Provider 建用户+入组+授权；已有 email = 直接入组）→ 更新邀请状态
- **集成**: 建用户（`POST /api/users` 支持 password ✅）/入组/授权经 Provider；Logto 原生组织邀请 API 存在（`/api/organization-invitations` 全套）但**决策维持自建**（IAM 无关性）；备选增强: Logto 邮箱域 JIT 供给（`/api/organizations/{id}/jit/email-domains`）
- **注意**: 建用户+入组+授权为 3 次独立调用**无原子性** — 接受流程需幂等设计（先查后建、失败重试不重复建号）
- **实现**: 邀请 CRUD（`InvitationsService` 现为 **4 行空类**）、Token 生成/验证/过期、公开注册页面、邮件服务（SMTP — `mail.config.ts` DTO 已定义未使用）
- **现状**: ❌ 流程完全未实现；`UserInvitation` 模型已有（含 organizationId/roleIds/status/expiresAt 字段，缺 tenantId）

### 4.6 审计日志（租户化） 【实现】 P2

- **做什么**: 加 tenantId；操作记录接入认证后的真实用户身份（当前 userId 是裸字段无来源）；查询按租户过滤
- **现状**: ⚠️ `AuditLogRepository` 已有（记录/查询/统计），`audit-logs.service` 已有

### 4.7 用户扩展信息（租户化） 【实现】 P2

- **现状**: ⚠️ `UserExtendRepository` 已有（部门/职位/风险等级统计）；模型缺 tenantId

### 4.8 批量操作 / 系统通知 / 数据统计 【实现】 P3

- **批量操作**: `BatchOperation` 模型已有，无任何 service/controller — 全新实现（用户导入/批量分配角色）
- **系统通知**: `UserNotification` 模型已有，无 service — 全新实现
- **数据统计**: ⚠️ `statistics.service.ts`（93 行）已混合调用 LogtoService + AuditLogRepository + Prisma（半真），需租户化 + 会话数据接入（现有 TODO）

## 八、Logto 能力调研结论 ✅（2026-09-18，基于 docs.logto.io + openapi.logto.io）

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | 用户可否同时属于多个 Organization | ✅ **原生支持**（官方多租户 SaaS 文档模式）；Cloud 限额: 每实例 org 数（Dev 5k/Pro 100k）、每 org 用户数 100k；**org/用户 无文档化上限**；OSS 无文档化限额 | plan-your-architecture / system-limit |
| 2 | org 角色按组织差异化 | ✅ **原生支持** — "Each user can have different roles in different organizations"；角色为模板级定义（全实例共享），按用户×组织分配 | endpoint-organizations 组描述 |
| 3 | 查询用户组织列表 | ✅ `GET /api/users/{userId}/organizations`（含每组织的 organizationRoles；无分页参数） | operation-listuserorganizations |
| 4 | Logto 原生组织邀请 | ✅ **存在全套 API**（创建/邮件/状态/一次性 Token）；接受时须绑定已有 userId（acceptedUserId），接受页为应用侧自建。**决策维持自建邀请库**，Provider 作可选能力暴露 | endpoint-organization-invitations |
| 5 | 建用户+入组+密码原子性 | ✅ `POST /api/users` 支持 password/passwordDigest；⚠️ **无单一原子端点** — 建用户→入组→授权为 3 次调用，需幂等设计 | operation-createuser 等 |
| 6 | 应用按 Organization 隔离 | ❌ **交互式 OIDC 应用实例级全局**，仅 M2M 应用可关联组织。租户应用接入配置必须自建（4.4 拆分成立）；租户级 API 授权可用组织 Token/组织级 API 资源 | understand-how-organizations-work |
| 7 | Organization 自定义数据 | ✅ `customData` 任意 JSON（创建/更新/查询均支持） | operation-create/updateorganization |
| 8 | OSS vs Cloud | ✅ **组织全家桶均在 OSS**（org/角色/邀请/JIT/SP 发起企业 SSO）；Cloud 独有: 多租户 Console、IdP 发起 SSO、SAML 应用>3 等；❌ **SCIM 两者均不支持**（需 webhook/Management API 自建） | logto-oss 页 |
| 9 | JIT 供给 | ✅ **原生支持**两种: 企业 SSO JIT + 邮箱域 JIT（`/api/organizations/{id}/jit/*` 可配置默认角色）；仅用户发起动作触发，不影响 Management API | just-in-time-provisioning |
| 10 | 术语澄清 | Logto Cloud "tenant" = 隔离实例（`[tenant_id].logto.app`）；Organization = 实例内组织；**OSS 一实例一租户**，多实例=多部署。我们的"软隔离"正是官方文档推荐模式 | automate-tenant-creation / plan-your-architecture |

**总体结论**: "租户 = Logto Organization + 软隔离"架构**完全可行**，是 Logto 官方文档化的多租户 SaaS 模式。多租户归属的缺口 100% 在我方（Tenant 模型/认证/租户化），不在 Logto。

> 注: openapi.logto.io 文档面向 Logto Cloud；自部署 OSS 实例以 `/api/swagger.json` 为准（端点面一致，以实例为准）。

## 九、扩展机会：我们还可以做什么（当前未涉及）

> 定位之内、主线规划之外的机会空间。三档：**T1** = Logto 原生能力，Provider 封装即启用；**T2** = 平台自建增值（差异化）；**T3** = 远期企业级。均不改变第七节 P0-P3 主线，作为路线图储备。

### T1 — Logto 原生、尚未规划的能力（调研已证实存在）

| # | 能力 | 说明 | 价值 | 前置 |
|---|------|------|------|------|
| T1.1 | **租户级企业 SSO（自带 IdP）** | 每组织关联企业 SSO 连接器（SAML/OIDC，SP 发起，**OSS 可用**），租户员工用自己公司的 Okta/Azure AD/Google Workspace 登录 | B2B SaaS 刚需，租户粘性核心 | 封装 `/api/organizations/{id}/jit/sso-connectors` + 租户设置页 |
| T1.2 | **邮箱域 JIT 自动入组** | 租户配置邮箱域名后，该域名邮箱注册的用户自动入组+默认角色（`/jit/email-domains`） | 邀请之外的零摩擦扩员通道 | 同上，与 4.5 邀请互补 |
| T1.3 | **租户级 MFA 强制** | 组织级 `isMfaRequired` 开关 | 安全基线，企业客户常要求 | Provider 封装 + 设置页 |
| T1.4 | **组织 Token / 组织级 API 资源** | 租户自己的下游应用用组织 Token 获得租户作用域的 API 授权 | "应用接入"从配置管理升级为真实授权能力 | Provider 封装 + 接入文档 |
| T1.5 | **租户品牌化（登录页）** | 组织级 branding（logo/颜色/自定义 CSS），租户登录体验自有品牌 | white-label 卖点 | Provider 封装 + 设置页 |
| T1.6 | **Webhooks 事件同步** | 订阅 Logto 组织事件（成员变更等），驱动扩展库缓存刷新与通知 | 数据新鲜度 + 事件驱动 | 后端 webhook 接收端点 |
| T1.7 | **M2M 应用组织关联** | 租户的后端服务（M2M 应用）关联组织并授予 org 角色 | 服务间授权场景 | Provider 封装 |

### T2 — 平台自建增值（差异化）

| # | 能力 | 说明 | 价值 | 前置 |
|---|------|------|------|------|
| T2.1 | **终端用户自助中心** | 面向租户成员（非管理员）的个人中心：资料自改、改密、MFA 设置、我的会话/设备 | 从"管理台"扩展为完整"用户平台"，贴合 IAM 定位 | 认证完成后即可做 |
| T2.2 | **会话与设备管理** | 管理员/用户查看活跃会话并强制下线 | 安全运营刚需；顺路解决 statistics 的 activeSessions TODO | Logto 会话 API 封装 |
| T2.3 | **SCIM 目录同步（自建）** | Logto 无 SCIM（调研确认）；我们可在 Management API 之上为每租户暴露 SCIM 端点，企业客户用 IdP/HR 系统直接同步用户 | **差异化卖点**——补上 Logto 生态空白 | P1 用户管理完成后 |
| T2.4 | **通知渠道扩展** | 现有 UserNotification 仅站内；扩展邮件/webhook/IM（Slack/飞书/钉钉） | 邀请、审批、告警触达 | 邮件服务（6.2）先行 |
| T2.5 | **租户开放 API** | 租户用 API Key 程序化访问平台（用户数据、审计） | 租户集成场景 | P0 认证 + API Key 体系（jwt.config DTO 已有雏形） |
| T2.6 | **安全分析** | `UserExtend.riskLevel` 字段已有；登录历史、异常检测、风险趋势 | 安全增值模块 | 审计日志租户化（4.6） |
| T2.7 | **动态用户分组** | 按条件（部门/标签/风险级）建用户段，用于批量操作与策略 | 批量操作（4.8）的放大器 | P3 |
| T2.8 | **多语言 i18n** | 界面多语言，租户级语言偏好 | 国际化租户 | 前端基建 |
| T2.9 | **用户跨租户归属视图** | 管理员查看某用户归属的所有租户及各租户角色，支持跨租户调动 | 软隔离 SSO 特性的管理面 | 3.3 租户成员关系 |

### T3 — 远期企业级

| # | 能力 | 说明 | 备注 |
|---|------|------|------|
